# Migrating a legacy suite to bnrest

The strangler pattern (spec §18) — follow this for each of the 11 legacy
suites not yet migrated (see `test-migration-map.md` for the exact
per-test rollout order and suite groupings).

## The rule that matters most

**Do not delete or disable a legacy test until its replacement exists,
executes, covers the same request + assertions, is in
`test-platform/migration-manifest.json`, and passes a parity check.** The
legacy suite (`test-automation/rest-assured-suite`) stays fully intact and
`make test-legacy` keeps running it for as long as any manifest entry is
`pending`.

## Steps (worked example: the Authentication migration already done)

1. **Read the legacy class.** `AuthSuite.java` — note its shared helpers
   (`Api.loginAsAdmin()`), its ordered `@Test` steps, its tags, its
   `@DisplayName` (carries the plan's `TC-AUTH-NNN` id).
2. **Extract the repeated operation into ONE Util**, if there is one.
   `Api.loginAdmin(email, password)` → `AUTH-UTIL-001` (see
   `writing-utilities.md`). Check `current-test-inventory.md`'s
   "Duplicate/near-duplicate logic already identified" section for
   candidates already flagged (`ENQUIRY-UTIL-001`, `ROOM-UTIL-001` are
   next).
3. **One bnrest Case per legacy `@Test` method** — or a merged case where
   two legacy methods really test one flow (`tc_auth_001_validLoginSucceeds`
   + `tc_auth_001b_tokenIsUsable` → one `AUTH-TC-001`, since "log in, then
   use the token" is one flow, not two independent tests).
4. **Assign the new id** using the domain-prefix convention already
   established in the manifest (see `test-numbering.md` and
   `test-migration-map.md`'s "Suite-grouping rationale") — don't invent a
   new prefix ad hoc.
5. **Write the suite file**, `Call CatchError`-ing every new case.
6. **Wire it into `COL-FUNC-001`** (one `Call CatchError` line).
7. **`make test-validate`** — zero cycles/missing-refs/duplicate-ids.
8. **Run both suites against the same live backend** and compare:
   ```bash
   make test-legacy   # confirm the legacy class still N/N passing
   make test-new       # confirm the new suite N/N passing
   ```
9. **Record parity** in `test-platform/migration-manifest.json` (set
   `migrationStatus: completed`, `parityStatus: verified` for each migrated
   legacy method) and write/update a `test-results/migration/parity-report.md`
   entry (see the Auth one as a template) comparing endpoint + assertion
   coverage, not just pass/fail counts.
10. **Do NOT delete the legacy class yet** unless this is the very last
    suite remaining — Phase F requires ALL suites at verified parity first.

## Every legacy test must appear in the manifest

`test-platform/migration-manifest.json` already has an entry for every one
of the 109 real legacy tests (generated by walking
`test-automation/rest-assured-suite/src/test/java/**/*.java`), each with
`legacyClass`/`legacyMethod`/`legacyId`, a pre-assigned `newTestId` and
`newFile` path, and `migrationStatus: pending` / `parityStatus:
not-verified` until you do steps 8–9 above. Update the SAME entries in
place — don't add duplicates.

## New coverage with no legacy equivalent

If migration surfaces a gap the legacy suite never covered (like
`AUTH-TC-004`'s CSV-driven credential sweep), add a manifest entry with
`legacyClass`/`legacyMethod`/`legacyId` all `null`, a `note` explaining why,
`migrationStatus: completed`, `parityStatus: "n/a-new-coverage"`.
